# Schema Conventions

The rules the schema follows, and the rules it leaves to the application.

## Naming

- Models are singular PascalCase (`ItemCollection`); tables are plural snake_case via `@@map` (`item_collections`).
- Columns keep Prisma's camelCase names (`emailVerified`, `isPro`) — except the NextAuth `accounts` columns, which use the snake_case names the adapter expects (`access_token`, `expires_at`).
- Booleans read as questions: `isPro`, `isPinned`, `isFavorite`, `isSystem`.

## Ids and timestamps

- Every primary key is a `cuid()` string, generated by Prisma — not a database sequence. Ids don't reveal counts or order.
- Join tables use a composite primary key (`item_collections`: `itemId` + `collectionId`).
- Tables with user-editable rows have `createdAt` (`@default(now())`) and `updatedAt` (`@updatedAt`, set by Prisma on every update).

## Ownership and deletes

- Every user-owned table has a `userId` foreign key with `onDelete: Cascade`, so deleting a user removes everything they own in the database.
- Joins cascade from both sides.
- `items.itemTypeId` does **not** cascade: an item type in use can't be deleted.
- Ownership is enforced by the application — every query filters by `userId` — not by the database. See the [security model](../architecture/security-model.md#tenancy).

## Text and JSON

- Long, user-supplied text uses `@db.Text` (`content`, `description`, OAuth tokens).
- Structured per-user settings are a single `Json` column (`users.editorPreferences`), merged over code defaults on read, rather than a column per setting.

## What the schema doesn't enforce

These are application rules only. A direct write through Prisma Studio or a script can break them:

| Rule | Enforced in |
|---|---|
| Only the payload columns of an item's content type are set | `createItem`, `updateItem`, the import action |
| An item's collections belong to the same user as the item | Not enforced — see [known gaps](../known-gaps/not-yet-built.md#security) |
| A `fileUrl` points into the owner's `{userId}/` prefix in R2 | Not enforced — see [known gaps](../known-gaps/not-yet-built.md#security) |
| Free users have at most 50 items and 3 collections | `lib/usage.ts`, checked before a create (not atomically — two concurrent creates can both pass) |
| System item type names are unique | The seed checks before creating; the (`name`, `userId`) unique constraint doesn't apply because PostgreSQL treats the `null` user ids as distinct |
